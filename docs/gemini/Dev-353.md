## Summary

This report evaluates the proposed design for the live pump-loop ladder executor (Dev-353) against `server.js` and standing engineering decisions. Four high-severity findings were identified: an existing violation of decision D15 in `autoExecuteSell` (reading available holdings instead of available + reserved), an array search bug in `getAvailableUSD` that ignores USD cash when USDT is present, hardcoded UUID generation in `placeRevolutOrder` blocking crash-intent recovery, and unconfirmed order states during crash recovery. A complete state/race matrix, failure ranking, and implementation spec for Claude are provided.

## Findings

1. **HIGH: `autoExecuteSell` violates Standing Decision D15 and lacks ladder-execution options**
   - **Evidence**: `server.js` in `autoExecuteSell`:
     ```javascript
     const asset = balancesNow.find(b => b.currency === coinBase);
     const currentQty = parseFloat(asset?.available || 0);
     ```
   - **Why it matters**: Standing Decision D15 requires reading `available + reserved` for total holdings. Reading `available` alone undercounts position size when tokens are reserved in limit orders or card authorizations. Furthermore, `autoExecuteSell` currently triggers `cascadeRulesAfterTrade` when a pump rule exists, which would spawn duplicate single-mode buyback engines alongside the ladder unless `skipCascade: true` and `clientOrderId` options are supported.

2. **HIGH: `getAvailableUSD` array search bug returns single match and fails for `-USD` market buys**
   - **Evidence**: `server.js` in `getAvailableUSD`:
     ```javascript
     const usd = balances.find(b => b.currency === 'USD' || b.currency === 'USDT');
     return parseFloat(usd?.available || 0);
     ```
   - **Why it matters**: `Array.prototype.find` returns only the first matching currency in `balances`. If `USD` is $0 and `USDT` is $500, but `USD` appears first in the array, `getAvailableUSD` returns 0. Furthermore, Revolut X market buys for `-USD` pairs require `USD` cash; quote-size USD buys fail if available USD cash is zero (even if USDT is held).

3. **HIGH: `placeRevolutOrder` hardcodes internal `clientOrderId` generation**
   - **Evidence**: `server.js` in `placeRevolutOrder`:
     ```javascript
     async function placeRevolutOrder(symbol, side, orderType, baseSize, price = null, valueUsd = null) {
       const clientOrderId = randomUUID();
     ```
   - **Why it matters**: Proposed Design Point 5 requires persisting intent with a `clientOrderId` prior to execution. Because `placeRevolutOrder` ignores caller-supplied UUIDs and generates a new `randomUUID()` internally, the intent `clientOrderId` recorded in `ladder_live` state will never match the `client_order_id` in `pending_orders` or Revolut X. On crash recovery, intent confirmation is impossible.

4. **HIGH: Crash recovery risk from API eventual-consistency lag and unconfirmed intent timeouts**
   - **Evidence**: Proposed Design Point 5 in ticket #353:
     > "Next tick, if an intent exists, confirm it BEFORE anything else (pending_orders by client_order_id; holding/USD change vs the snapshot)"
   - **Why it matters**: If a server restart occurs mid-flight, Revolut X API balance updates can lag order fills by several seconds. Relying on balance snapshots (`holding_before` / `usd_before`) alone will misdiagnose a filled order as unconfirmed. In accordance with decision D14 (crash-safe ordering), intent MUST be confirmed via `pending_orders` / Revolut X order status first, and intent state updated before any new tick evaluation occurs.

5. **MEDIUM: Race condition when Bryan manually trades or exits mid-cycle**
   - **Evidence**: `server.js` in `syncRevolutLotsDownToBalance`:
     ```javascript
     await syncRevolutLotsDownToBalance(coinBase);
     ```
   - **Why it matters**: If Bryan manually sells 100% or part of his position in the Revolut app while a ladder cycle is active, real holdings drop. If the ladder evaluator state (`state.qty`) is not synchronized with real holdings (`min(REAL holding available+reserved, cap_usd / start_price)`), the ladder will attempt to sell tokens that Bryan no longer owns, or buy back proceeds for a position that was fully exited.

6. **MEDIUM: Absence of re-entrancy / tick-overlap lock in `runFastScan`**
   - **Evidence**: `server.js` in `runFastScan`:
     ```javascript
     async function runFastScan() {
     ```
   - **Why it matters**: `runFastScan` executes every 30 seconds. Network latency or venue API slowdowns during market order execution can cause a tick to exceed 30 seconds. Without an in-memory execution lock (e.g. `_ladderLiveBusy`), concurrent ticks will evaluate the same uncommitted state and place double sell or buy market orders.

7. **MEDIUM: Incomplete disarming when single-mode pump loop is converted to ladder mode (#6)**
   - **Evidence**: `server.js` in `manage_auto_rules`:
     ```javascript
     await db.execute('UPDATE pump_armed_rules SET loop_enabled = 0 WHERE symbol = ?', [sym]);
     ```
   - **Why it matters**: Simply setting `loop_enabled = 0` leaves active `troughTrackers` in memory and resting trailing stops in `trailing_stops`. Enabling ladder mode must atomically clear `troughTrackers`, `standaloneTroughTrackers`, `trailing_stops`, and refuse activation if single-mode has a live cycle in progress (`sale_price IS NOT NULL`).

8. **LOW: Telegram notifications lack distinct live vs shadow formatting**
   - **Evidence**: `server.js` in `runLadderShadowTick`:
     ```javascript
     await sendTelegram('🧪 <b>SHADOW ' + coin + '</b> - paper only, nothing traded\n\n' + msgs.join('\n') + ...
     ```
   - **Why it matters**: Real live orders must be unmistakably distinct from shadow paper trades (#358) to prevent confusion. Live orders must broadcast `🚨 <b>LADDER - REAL ORDER EXECUTED — COIN</b>` with fill prices, quantities, and remaining ring-fenced USD.

### Failure Modes Ranked by Financial Risk

1. **Double Sell / Double Buy on Server Restart or Stalled API Call (CRITICAL)**
   - *Mechanism*: Order placed on venue, server crashes or HTTP stalls >30s. Tick N+1 re-evaluates uncommitted state and places a second market order.
   - *Mitigation*: In-memory tick lock (`_ladderLiveBusy`) + persist Intent with deterministic `clientOrderId` BEFORE order HTTP call. Confirm intent before any new tick evaluation.

2. **Buying with Unfunded / Phantom Cash due to `getAvailableUSD` bug (HIGH)**
   - *Mechanism*: `getAvailableUSD` returns incorrect cash or picks USDT when USD is needed for `-USD` market buys, causing order rejection or market buy failure.
   - *Mitigation*: Fix `getAvailableUSD` to check exact currency needed (`USD`) and ensure available USD is strictly verified before placing market buy.

3. **Selling Below Cost Basis due to `autoExecuteSell` D15 undercount (HIGH)**
   - *Mechanism*: `autoExecuteSell` reads `available` instead of `available + reserved`. If reserved > 0, `currentQty` is undercounted, calculating a smaller sell size, or if floor check is bypassed/miscalculated.
   - *Mitigation*: Fix `autoExecuteSell` to read `available + reserved` (D15 compliance) and pass `entry_floor` / `sell_floors` checks.

4. **Duplicate Buyback Engines chasing same pullback (HIGH)**
   - *Mechanism*: Ladder sell triggers `autoExecuteSell`, which spawns Stage-3 single-mode `cascadeRulesAfterTrade` rebuy engine while ladder's own buy-tier engine is watching the same drop.
   - *Mitigation*: Pass `skipCascade: true` to `autoExecuteSell` when called from ladder.

5. **Runaway Loop Re-arming Forever (MEDIUM)**
   - *Mechanism*: Price whipsaws around peak + 1% re-arm level, triggering repeated sell legs up to `max_legs` without cap safeguards.
   - *Mitigation*: Strictly enforce `max_legs` (default 2) per cycle and `min_tier_usd` dust guard.

6. **Stale State after Manual Full Exit (MEDIUM)**
   - *Mechanism*: Bryan exits coin manually; ladder keeps running in DB on phantom state.
   - *Mitigation*: Every tick checks `REAL holding available+reserved`. If holding == 0, halt cycle, set `active = 0`, and notify Telegram.

## Recommendations for Claude

### Design Point Evaluation (Points 1–7)

- **Point 1 (Table `ladder_live` & system_config `ladder_live_enabled`)**: **KEEP & EXTEND**.
  - *Keep*: Dedicated table `ladder_live` and global switch `ladder_live_enabled`.
  - *Add*: Include an `intent` LONGTEXT/JSON column in `ladder_live` for crash-safety intent tracking. Create `ladder_live_fills` for execution history.

- **Point 2 (Position & USD Sizing per tick)**: **CHANGE**.
  - *Change*: Position size MUST use `available + reserved` (D15 compliance). Sizing USD for buys MUST check available `USD` cash (fixing `getAvailableUSD`).

- **Point 3 (SELL leg via `autoExecuteSell`)**: **CHANGE**.
  - *Change*: Update `autoExecuteSell` to accept an `options` object `{ skipCascade, clientOrderId, source }`. Update `autoExecuteSell` to read `available + reserved` for total position calculation. Skip `cascadeRulesAfterTrade` when `skipCascade === true`.

- **Point 4 (BUY tier via `placeRevolutOrder`)**: **CHANGE**.
  - *Change*: Modify `placeRevolutOrder` signature to accept an optional caller-supplied `clientOrderId` parameter (`callerClientOrderId = null`). If provided, use it instead of generating a new `randomUUID()`.

- **Point 5 (CRASH SAFETY & Intent Confirmation)**: **KEEP & STRENGTHEN**.
  - *Keep*: Persist intent BEFORE placing order.
  - *Strengthen*: Store intent in `ladder_live` prior to API invocation (D14 compliance). Confirm intent on next tick via `pending_orders` by `client_order_id` or Revolut X `/orders/historical` API before re-evaluating state. If unconfirmable after 3 minutes, halt coin (`active = 0`) and alert via Telegram.

- **Point 6 (ONE ENGINE PER COIN)**: **KEEP & ENFORCE**.
  - *Keep*: Refuse Kraken coins in v1.
  - *Enforce*: On ladder enablement, check if single-mode cycle is live (`pump_armed_rules.sale_price IS NOT NULL` or active `troughTrackers`). If live, refuse. Disarm single-mode loop (`loop_enabled = 0`, clear `armed`, remove trailing stop in `trailing_stops`, clear `troughTrackers` & `standaloneTroughTrackers`).

- **Point 7 (Telegram Notifications)**: **KEEP**.
  - *Keep*: Format distinct alerts: `🚨 <b>LADDER - REAL ORDER EXECUTED — COIN</b>` with fill details, leg/tier, remaining reserved USD, and current cycle state.

### Step-by-Step Build Instructions for Claude

1. **Database Tables**:
   - Create table `ladder_live` (symbol VARCHAR(20) PRIMARY KEY, cfg TEXT NOT NULL, state TEXT NULL, intent TEXT NULL, cap_usd DECIMAL(20,4) NOT NULL, active TINYINT(1) DEFAULT 0, created_at TIMESTAMP, updated_at TIMESTAMP).
   - Create table `ladder_live_fills` (id INT AUTO_INCREMENT PRIMARY KEY, symbol VARCHAR(20), cycle_id VARCHAR(32), leg VARCHAR(8), tier INT, price DECIMAL(30,12), qty DECIMAL(30,10), usd DECIMAL(20,6), client_order_id VARCHAR(64), order_id VARCHAR(64), status VARCHAR(20), note TEXT, created_at TIMESTAMP).

2. **Core Function Updates in `server.js`**:
   - **`placeRevolutOrder`**: Update signature to `placeRevolutOrder(symbol, side, orderType, baseSize, price = null, valueUsd = null, callerClientOrderId = null)`. Use `callerClientOrderId || randomUUID()`.
   - **`autoExecuteSell`**:
     - Update position calculation: `const currentQty = parseFloat(asset?.available || 0) + parseFloat(asset?.reserved || 0);` [D15].
     - Support options: `autoExecuteSell(symbol, maxPct, analysis, confidence, options = {})`.
     - Pass `options.clientOrderId` to `placeRevolutOrder`.
     - Skip `cascadeRulesAfterTrade` when `options.skipCascade === true`.
   - **`getAvailableUSD`**:
     - Update `getAvailableUSD(exchange, currency = 'USD')` to find exact currency matches (`USD` vs `USDT`), returning available balance for the specified currency.

3. **Live Ladder Execution Engine (`runLadderLiveTick`)**:
   - Add re-entrancy lock `_ladderLiveBusy` in `runFastScan`.
   - Check `system_config` key `ladder_live_enabled === 'true'`.
   - Iterate over active `ladder_live` rows:
     a. **Intent Recovery Step**: If `intent` exists in DB:
        - Query `pending_orders` by `client_order_id`.
        - If found and status in (`filled`, `pending_new`, `new`, `partially_filled`): update evaluator state in DB, clear `intent`, log fill.
        - If not in `pending_orders`: query Revolut X `/orders/historical` or `/orders/{id}`.
        - If unconfirmable and `Date.now() - intent.at > 180000` (3 mins): set `active = 0`, notify Telegram "LADDER HALTED — UNCONFIRMED INTENT", do not place order.
     b. **Holding & Cash Verification**:
        - Fetch real balance (`available + reserved`). If 0, halt ladder (`active = 0`), notify Telegram, clear state.
        - Calculate `position = min(REAL holding available+reserved, cap_usd / start_price)`.
        - Fetch real available `USD` cash.
     c. **Evaluator Step**:
        - Run `shadowEvalLadder` on a copy of state.
     d. **Order Execution & Intent Persistence (D14)**:
        - For a sell fill: generate `clientOrderId`, write `intent` to DB -> call `autoExecuteSell(symbol, sellPct, analysis, 'High', { skipCascade: true, clientOrderId, source: 'ladder' })` -> update state, clear intent, send Telegram.
        - For a buy fill: generate `clientOrderId`, write `intent` to DB -> call `placeRevolutOrder(symbol, 'buy', 'market', null, null, buyUsd, clientOrderId)` -> update state, clear intent, send Telegram.

4. **MCP & Control Commands**:
   - Add actions to `manage_auto_rules`: `ladder_live_start`, `ladder_live_stop`, `ladder_live_status`.
   - On `ladder_live_start`: perform single-engine checks (#6), disarm single-mode pump loop & trailing stops, populate `ladder_live`.
