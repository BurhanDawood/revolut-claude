## 1. System Overview

A personal, single-user automated crypto portfolio manager. It monitors holdings across Revolut X and Kraken, tracks tax lots, fires price/structure/macro alerts to Telegram, executes trades through a Telegram-gated approval flow, and surfaces AI analysis and live web research. The owner is the sole decision-maker; the system is an assistant and a safety net, not an autonomous trader.

**Stack**
- **Runtime:** Node.js (v22) / Express, single `server.js` (35,412 lines at #625; 2.8 MB). The app shell, the family page and the agent/desk pages are served from HTML/JS strings inside it.
- **Database:** MySQL on Railway (`mysql.createPool` with `connectionLimit: 10`, `waitForConnections: true`, `enableKeepAlive: true`, `keepAliveInitialDelay: 10000`).
- **Hosting:** Railway (service `revolut-claude-production.up.railway.app`), 1 replica, US-West, deploys from GitHub on push.
- **Interfaces:** Telegram bot (alerts, trade approval, every money button), a web dashboard (`public/dashboard.js`), the phone app shell (`/app`, §1.4), the Android app and its Galaxy Watch companion (`mobile/`, §1.4), the family page (`/h/<key>/`, §1.6), and an MCP server (`/mcp-<MCP_PATH_SECRET>`, 32 tools) for the Claude threads.
- **External APIs:** Revolut X (primary exchange), Kraken (secondary: GHIBLI, ZK, XPL, TAO), Tangem (XRP cold-storage balance), Anthropic (Sonnet 4.6 alert paths, Sonnet 5 agents, Haiku screens, Fable 5.1 senior diff review), Google Gemini (morning brief, video notes, feed analysis, desk drafts, agent research), Firebase Cloud Messaging (app push), YouTube Data API, Telegram Bot API, Google Drive (nightly backups).
- **Repo:** `github.com/BurhanDawood/revolut-claude` (public). **Local:** `C:\Users\owner\revolut-claude\server.js`.

**Secrets (Railway env vars only, never chat, notes, the desk or the APK):** venue keys (`REVOLUTX_*`, `KRAKEN_*`), `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `YOUTUBE_API_KEY`, `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` / `TELEGRAM_WEBHOOK_SECRET`, `FCM_SERVICE_ACCOUNT`, the Google OAuth set for backups, and the access keys of §1.7 (`DASHBOARD_TOKEN`, `WATCH_TOKEN`, `FAMILY_PAGE_TOKEN`, `MCP_PATH_SECRET`, `DEV_LOG_TOKEN`, `EXPORT_TOKEN`, `BRIDGE_TOKEN`; `API_TOKEN` deliberately unset). Credential bugs are diagnosed via length/char-code checks, never by echoing values.

### 1.1 The working threads

Development and operation are split across Claude contexts, by design (today: the PM thread, the Dev thread and Fable in claude.ai, plus Claude Code sessions with the repo attached for the Android/watch app, which push to the `mobile-app` branch only):

- **PM thread** — portfolio manager. Handles analysis, alerts, trade logging, strategy reviews, morning briefings. Reads/writes the database via MCP tools. Never edits code.
- **Dev thread** — lead developer / diagnostician. Diagnoses read-only against the live code (pulled from GitHub raw / Drive sync), writes Cowork prompts, verifies read-backs, manages the `dev_log`. Never edits live code directly.
- **Cowork** — a separate PC agent that performs the actual file edits and runs `PUSH_NOW.bat` to commit/deploy. Receives single-box prompts from the Dev thread, writes its read-back to a Google Drive folder the Dev thread reads directly. *(Historical — superseded in September 2026 by batches applied through the Apply Batch Patch GitHub Action; see §5.)*
- **Senior-review thread** (from 23 Sep 2026, Claude Fable) — reviews the hardest problems in depth (state that gates execution, money-accounting integrity, strategy, CC). Writes **specs** — anchor text, exact edits, tests incl. restart cases — and never builds; the Dev thread builds, tests and ships them one batch each, so `server.js` has a single builder.

This separation is deliberate: the Dev thread reasons and verifies but cannot push; Cowork executes but does not design. Every change passes through a written prompt + a verified read-back before deploy. The same `cross_thread` principles (auto-exec-off, never-sell-below-entry, etc.) are surfaced in both PM and Dev session briefings (see §3, decision-memory layer).

A failed or malformed answer escalates.

- A held run (`screen_hold`) trades nothing and keeps Sonnet's own alerts, notes and watch list. It re-arms the position alerts (`agentArmPositionAlerts`: stop_price and the drop), which expire after 6 hours.
- Every `route_shadow_every`-th (2nd) held run, in the first `route_shadow_days` (14) after the clock start, also asks Sonnet (`agentShadowSonnet`). The answer is logged only: never executed, and not charged to the paper cash.

The routing may be put forward for a live design only after two weeks at about 90% agreement on entries over at least 25 compared runs; otherwise Sonnet decides every run.
- Every `agent_decisions` row carries `route` and `settings_ver` (the `agent_changes` id in force). The scorecard lists every closed trade against holding BTC over the same hold, with its settings version at entry and exit; under 5 scored trades it says "insufficient".
- **The go-live clock** (`system_config` `agent_clock`) is written once, 45 s after the first boot of 549 (`agentClockStart`, INSERT IGNORE). The bar is measured from it: 30 days AND 10 closed trades, whichever takes longer (#552).

## 2. Data-Flow Map

### 2.1 The main monitoring loop
`checkPortfolio()` runs every 5 minutes. It pulls live tickers from Revolut X (one `/tickers` call → a price map of ~788 entries), pre-loads Kraken-only coins (GHIBLI, XPL, TAO) via Kraken, loads 24h baseline prices from `price_history`, then iterates every held/watched coin: computes % move vs 24h, skips dust (<$1 position value), and evaluates alert conditions (fixed targets, daily-move thresholds, trailing stops, auto-rules). The same loop hosts the card-payment auto-log detector (§2.7).

### 2.2 Intraday capture + abnormal-move detector (#50 Build 1 + Build 2)
`captureIntradayPrices()` runs every 2 minutes (decoupled from the 5-min loop). Captures all non-meta `coin_strategy` coins (held + watch) into `price_intraday`. This is the data clock for the abnormal-move detector. **#50 Build 2 shipped 2026-06-22:** after each capture insert, `evaluateAbnormalAlerts()` computes a per-coin volatility baseline (mean absolute %-move between consecutive 2-min captures over a 14-day lookback) and fires a Telegram alert when the latest move is both `>= ABN_K (3) × baseline` AND `>= 0.4%` (an absolute noise floor — without it, near-flat coins fire huge multiples on trivial wobble). Direction-labelled PUMP/DUMP, per-coin 30-min cooldown (`abnAlertState` Map), both directions. Alert-only, never an execution path. Live-inspectable at `GET /api/abnormal`. Validated: baselines map cleanly to coin character (BTC ~0.04%, CC ~0.06%, JTO ~0.22%).

### 2.3 Fast-cadence scan (#94 / #95 Stage 1)
`runFastScan()` runs on a tight cadence (30–60s) over a small set of flagged symbols. It checks pump-arm rules first (`checkPumpArm` — dormant detectors that arm a trailing stop on a qualifying pump, see §3 pump-loop) and then services any armed trailing stops. **Part C** services pump-loop trough-rebuy trackers (`troughTrackers.keys()`). **Part D** services standalone inverse trough-buy trackers (`standaloneTroughTrackers.keys()`). Decoupled from the 5-min loop so fast meme/volatile moves aren't missed between cycles. **#99 shipped 2026-06-20:** fast-scan is now fully dynamic — Part B evaluates `trailingStops.keys()` with a single batched `/tickers` call per 30s cycle; all armed trailing stops covered. `FAST_SCAN_SYMBOLS` retained for Part A pump-arm checks only.

### 2.5 Alert pipeline
Conditions evaluated in the 5-min loop → if fired and not in cooldown / not acknowledged → Telegram notify. Acknowledged-alert state persists to `macro_alerts_sent` (so redeploys don't re-fire — #70). Fixed-target cooldowns are 24h. Alerts are **notify-only**; automatic orders come only from the paths in §2.6 and §3.1–§3.3, each behind the master switch and its own gates.

### 2.6 Trade execution + approval path
A trade (from MCP `execute_kraken_trade` or the Revolut path) creates a *pending* trade → Telegram "approval needed" → owner replies 👍 / approve → execution → journal write + tranche update. **All `/api/*` write routes require `x-api-token`** (#43, fail-closed); the critical trade endpoints reject unauthenticated calls with 401 before reaching the handler. Known limitation: the approval handler tracks only the most-recent pending trade, so laddered multi-rung approvals clobber each other (#44, open).

**Two-way Telegram interface (#316).** Alerts sent to Telegram feature inline-keyboard buttons generated by `buildAlertKeyboard` attached to `sendTelegram` messages. Taps arrive at `/telegram-webhook` as `callback_query` payloads and route through `processAlertChoice`. Button `callback_data` incorporates a compact alert-type guard (`a:<coin>:<choice>:<typeCode>`) that is verified against `alertContextBySymbol` to ensure taps on older messages do not execute against a superseded alert type. The interface also supports control commands: `/status` displays available USD cash, auto-exec state, cost basis, armed loops, and symbol constraints; `/pause` disarms `ai_auto_execute.enabled` in `system_config` (failing safe while in-flight cycles finish cleanly); and `/resume` requires explicit `/resume confirm` confirmation before re-enabling auto-execution.

**Auto-exec paths (multiple, all double-gated).** Several autonomous execution paths exist; each requires the global `ai_auto_execute` master ON plus a per-coin gate. (1) **Pump-loop** (#95): pump-arm → armed trailing stop → `autoExecuteSell`/`autoExecuteKrakenSell` → trough-rebuy (#130). (2) **Auto-exec trailing stop** (#93): trailing stops with `auto_execute:true` bypass Telegram approval on breach. (3) **Away Mode** (#125): fixed down-targets on away-active coins trigger AI analysis and buy if High confidence. (4) **Standalone trough-buy** (#143): `manage_alerts set_trough` arms an independent bounce-watcher. All paths carry hard entry-floor guards. The master (`ai_auto_execute.enabled`) is **ON** (13 Oct: `max_sell_pct` 100, `allowed_triggers` [trailing_stop], `per_coin_enabled` empty, `hodl_symbols` empty); the 5-min auto-rule path is alert-only since F2 (#397) — other auto-exec paths (#93, #125, #143) each have their own per-activation gates independent of `per_coin_enabled`.

### 2.7 Card-payment auto-log (#107)
Inside the 5-min balance loop, when USDT decreases with no offsetting balance increase (not a USD conversion, not a crypto buy, not recent trade-funding), the decrease is treated as a card payment: auto-logged to `trading_journal` (`source='revolut_card'`), invested capital decremented, and a one-way Telegram notice sent. A 15-minute dupe-guard prevents double-logging. Reversible anytime via `skip payment [amount]` (re-credits capital + deletes the row). This satisfies the #82 rule — capital is never *silently* mutated: every auto-log notifies and is reversible. Proven live 2026-06-17 (a real card payment auto-logged outside a redeploy window).

**Fiat withdrawal auto-log (#63, 2026-06-20).** Parallel detector: when USD (not USDT) decreases >$5 with no USDT-conversion offset and no recent crypto buy, the drop is auto-logged (`source='fiat_withdrawal'`), invested capital decremented, and Telegram notified. Reversible via `skip payment [amount]` (handler now covers both `revolut_card` and `fiat_withdrawal`). A 30-min dupe-guard on `withdrew X` prevents double-decrement if both auto-detect and manual reply fire for the same amount.

### 2.7b Locked balances and the card row's lifecycle (#537, with #486)
Revolut's `/balances` `reserved` holds two different things: coin held by this account's **own open orders**, and coin held for a **card payment that has not settled** (no order behind it). Every `GET /balances` is normalised in `revolutRequest` (`rxNormaliseBalances`): `reserved` keeps only what active orders hold (sells: coin left to sell; limit buys: USD left to spend, +1%); the rest moves to `locked`; Revolut's figures stay on the row as `reserved_raw` / `total_raw`. Holdings, values and sell sizes read the locked-aware figure. If `/orders/active` cannot be read (error, odd shape, more than one page) the balances are returned unchanged. A coin is first marked locked only after a fresh `/orders/active` read (no cache).

The **trade detector** (`previousBalances`, the 5-min loop and the qty-mismatch refresh) and the **lot sync** (`_syncRevolutLotsDownToBalanceNow`) read the **raw** total, so a hold never looks like a trade and never cuts lots. A coin card payment's life:
1. **Hold** — coin moves available → reserved; raw total unchanged. The card watch (#486) records the `payment` row (`card_pending`) at the hold. Holdings and sell sizes drop now (`locked`). Detector: no change.
2. **Settle** — the coin leaves; raw total drops. The detector sees the drop; `cardSpendSettles` consumes the payment row once its send is `completed`, so it is not logged as a sale; lots follow the raw total down. `locked` returns to 0.
3. **Release** (cancelled/declined) — reserved → available; raw unchanged, detector silent; the card watch reverses the payment row. `locked` returns to 0.

### 2.8 Reconciliation (#55)
Nightly at 3 AM: compares Revolut `/balances` (available) + Kraken balances against non-legacy tranche sums per `symbol,exchange`. Tolerance 0.5%; skips untracked/dust; tags `system > available` as possible open-order (a resting limit reserves coin). Telegram only on *new* drift. This institutionalised the manual ground-truth check that originally caught the #47 phantom-tranche bug.

### 2.9 Authoritative order reads (#326 Build 1)
`fetchExchangeOrders` pages Revolut X historical orders read-only, and `fetchOrderFills` retrieves per-order fill breakdowns (`GET /orders/${orderId}/fills`). Empirically established venue constraint: the `/orders/historical` endpoint is accepted with NO query string and rejected with ANY query string regardless of parameter encoding or signature scope. Consequently, `fetchExchangeOrders` queries the bare endpoint and performs date-range and symbol filtering client-side. Venue payloads deliver `created_date` as an epoch integer and symbols in slash form (`COTI/USD`), both normalized in runtime wrappers. Exposed via `GET /api/dev/orders-sync` and `get_trading_data include=['exchange_orders']`, this layer exists strictly to quantify tranche drift against exchange ground truth, not to mutate ledger state or fix drift.

Part B emits ranked, severity-sorted recommendations that each carry real ticket IDs: `stale_in_progress` (sev 4), `aging_backlog` (sev 2, deliberately collapsed to ONE summary line naming the oldest three after a dry-run showed a per-ticket list would emit wallpaper), `priority_queue_stale` (sev 3, fires on queue age >30d OR >=70% of its referenced tickets already resolved), `config_risk` (sev 3), `priority_queue_missing` (sev 3). Part C aggregates `dev_log` rows with `category='friction'`: an optional `tags: a, b, c` line in the entry detail takes priority, untagged rows fall back to free-text tokenising of title+detail, and each pattern is labelled `tagged`/`inferred`/`mixed`. The hybrid was chosen only after sandbox-comparing five variants against real data — pure free-text surfaced the author's writing habits (top hit was literally the word "friction") rather than failure classes. **Convention:** always end a friction entry's detail with a kebab-case `tags:` line.

- **#282 step 2 — Tiered pump-loop CONFIG (schema + validation only; nothing executes yet).** Six columns on `pump_armed_rules`: `rule_mode` (`'single'` by default, so every existing rule behaves byte-identically), `sell_tiers`/`buy_tiers` (JSON `[[trigger_pct, size_pct], ...]`), `tier_state` (engine-owned; never written by config), `tier_cooldown_min` (15 — governs intra-cycle tier fills, while the global `cooldown_minutes` still governs re-arming), and `min_tier_usd` (2.0 dust guard). The validator **rejects** an invalid or over-cap tier set outright and writes nothing; it never silently truncates. Cumulative sell is `1 - product(1 - p/100)` because each tier sells a share of the *current* position, so two 50/50 tiers come to exactly 75% of the original — compared against the live `max_sell_pct`. It also enforces a 6-tier maximum, strictly ascending triggers, and size in (0,100]. **The five tier columns use `COALESCE(?, col)` in the upsert rather than `VALUES()`**, so a later partial call that tweaks only `trail_pct` cannot silently wipe a tier set or flip `rule_mode` back to `single` — #281's lesson applied deliberately.
- **#278 — `manage_auto_rules action='reset_cycle'`.** The missing primitive for clearing pump-loop RUNTIME state while preserving CONFIG. Clears 11 fields (`armed`, `armed_since`, `sale_price`, `sale_proceeds_usd`, `reference_base`, `retrace_gate`, `trough_low`, `trough_armed`, `baseline_price`, `baseline_at`, `tier_state`) plus any in-memory `troughTrackers` entry, and touches **zero** config columns (audited programmatically before shipping). Refuses when `sale_price IS NOT NULL` — a genuinely live tracker — unless `force=true`, so it cannot silently abandon a pending rebuy; returns `cleared_from` so every reset is auditable. It exists because `loop_disable` only sets `loop_enabled=0` and leaves the row asserting state that is no longer true. **Why fossils accumulate:** the #130 rebuy ringfences sale proceeds expecting them to remain in the account; in practice the USD is often spent or moved, so when the bounce fires GATE 3 finds the balance short, notifies, and calls `clearTroughTracker()` — which clears the five trough fields but deliberately not `armed`/`armed_since`/`sale_proceeds_usd`. That is the exact signature seen across four rows in late July ($217.81 notionally ringfenced against $0.00 actual). The ringfencing model is intentionally unchanged: notify-and-abandon is the accepted behaviour. This also unblocks #269 (auto-disarm on zero position), which can now simply call `reset_cycle`.
- **#281 — `configure_auto_execute` merge-not-replace.** The handler previously rebuilt its config object from a hardcoded 9-key whitelist, silently dropping any key not on that list — `manual_only_symbols` vanished on every partial write. Fixed by spreading `...existingCfg` first so unmanaged keys survive while explicit params still override; this generalises to any future config key. A boot seeder independently re-patches `manual_only_symbols` when absent, which is why the fix deploy also self-healed the data. **#279** separately exposed `retrace_pct`/`bounce_pct` as setters on `set_pump_armed_rule` — both columns already existed and were already read by the trough logic, but had no way to be set.

### 3.1 Execution-safety layer (September 2026, batches #377–#405)

Every automatic order path now sits behind layered controls. Preventive controls constrain the *decision*; detective controls verify that a decision which should have executed actually did — the gap the HONEY incident exposed (dev log #397).

- **Derived sell floor (#377).** Every sell path uses `max(real cost x 1.005, any stored override)`: never below cost by construction. An override can raise the floor, never lower it.
- **Floor-capped EDGE sells (#387–#389, pm #44).** When a sale clears its floor by less than 3 x the coin's p90 sell slippage, it is placed as a LIMIT at the floor, rounded up to Revolut's `quote_step`, instead of a market order — it cannot fill below the floor. Any remainder is cancelled after ~12 s; only the actual fill is recorded. The first live EDGE sale is flagged for review.
- **Monitors.** Ring-fence coverage (:12/:42): buy-back cash vs available USD/USDT, allocated **largest-first** (A2). Stop clearance (#383–#386): write-time guard + `loop_audit` column + PASS/EDGE/DEAD state alerts with hysteresis.
- **Execution watchdog (#393, #399).** Cause-agnostic, read-only, every fast scan: **PAST** (price at/below an armed stop 3+ min, nothing acted), **STUCK** (armed, no trail, no buy-back), **HELD** (correctly held by `/pause`), **ORPHAN** (auto-selling trail on an unarmed loop). One Telegram per problem, one on recovery.
- **`/pause` is a true emergency stop (F1, #396).** Every autonomous order path reads `ai_auto_execute.enabled` fresh at fire time and **holds** while paused: trails stay armed, reservations kept, each hold reported once. `/resume confirm` restarts stale trough lows and lists everything that will act. Fails closed. Dashboard pause = full pause; resume is Telegram-only.
- **Auto-rules are alert-only (F2, #397).** `checkAutoTradeRules` never places an order (it had no master, floor or approval check).
- **Clear-first sells (F4, #398).** The auto-trail sell path removes its trail from memory **and** the DB before any venue call — no double sale after a restart or from concurrent scanners. DB failure = no sale. The #93 cooldown was then removed (F5b, #404).
- **Loop lifecycle.** `reset_cycle` removes the trail (F6). `setTrailingStop` auto-execute is three-valued — omitted preserves, `false` switches off (F3). An abandoned buy-back **reopens** the loop (`abandonCycle`, A1 #402/#403); a pending buy-back is abandoned after **14 days** or **48 h of missing cash** (A2 #405). `arm_events` records every arming.
- **Notification state never gates execution (#391–#393).** Acknowledgement and the Telegram "ignore" mute silence alerts only; they can never blind an auto-selling trail.
- **Money accounting (#395).** The payment detectors ask Revolut's own order history whether filled buys explain missing cash before calling it a payment; "Not a payment" cancels a still-held capital change instead of adding money back.
- **Stand-alone trough retrace gate (#394).** `set_trough` can stay dormant until a chosen price (`arm_below_price`, or `retrace_pct` + `reference_price`).
- **Fire-time predicate `mayAutoTrade` (#567, #604).** One fail-closed function (17810–18010) that reads the master switch, the rule, balances and the venue fresh, applies the derived floor, and writes an `exec_decisions` row for every verdict. In ENFORCE today for the single-mode loop's trough buy-back (a NO holds the cycle, re-asked every 5 min) and the paper agent; other callers run it as a dry run (the loop cards' Auto-sell line, #555).

### 3.2 Sell execution: chases, spikes and loop lifecycle (#454–#455, #558–#586)

- **Refused market sell → chase (#558, #573, #574).** When Revolut X cancels a trail's market sale at placement (thin-book slippage protection, #511 `venue_refused`), the sale falls back to a limit chase from the bid, re-read each step, never below the cost floor; the unfilled part re-trails as a % of the balance left.

- **Empty loops switch themselves off (#586).** A loop with nothing held for 72 h straight (real balance read; not Kraken, not Tangem XRP) is disabled by a compare-and-set writer.

## 4. Key Design Decisions (and why)

- **MySQL on Railway, single `server.js`.** One deploy target, one process, one DB; simple to reason about and cheap to run for a single user. Not split into services because the operational surface (one owner, one portfolio) doesn't justify the complexity.
- **Connection pool over single connection (#327).** Switched from a single `mysql.createConnection` to `mysql.createPool` (`connectionLimit: 10`, `waitForConnections: true`, `enableKeepAlive: true`, `keepAliveInitialDelay: 10000`). Operational lesson: a single `mysql.createConnection` has no automatic reconnect, so when the Railway MySQL connection dropped on 19 Sept 2026, every DB-dependent subsystem (price capture, order polling, portfolio checks, shadow evaluation, baselines) failed continuously for >2 hours while Express stayed up and reported the deployment healthy, preventing platform restart. Note: an explicit DB health check endpoint with alerting remains outstanding.
- **Auto-exec stays OFF by default.** The owner's edge is discretion; the documented weakness is rushed/FOMO decisions. The system defaults to *analyse-then-notify*, never *act*. Auto-exec, wherever enabled, is railed (caps, floors, manual-only symbols) and is the rare exception, not the norm. Enabling it is always a separate, deliberate decision in a fresh session — never bundled with the code change that built the path. The #95 pump-loop is the worked example: all four stages were built and deployed with the master OFF, so the irreversible action (the flip) stays decoupled from the build.
- **Double-gated autonomy.** Any autonomous loop requires two independent switches both ON (the global `ai_auto_execute` master AND a per-coin flag), so a single misconfiguration can't arm it. The pump-loop's `loop_enabled` is the per-coin gate.
- **Never sell below entry.** Every auto-sell path carries a hard entry-floor guard before it can fire; it fails safe (blocks) on uncertainty. A per-coin sell-floor (#45) remains the prerequisite before re-enabling any below-entry-capable trigger generally.
- **No leverage, no stop-losses.** The owner trades spot only and uses trailing stops to protect gains, never stop-losses. Generic "tighten your stops / leverage" boilerplate is wrong for this profile and must be stripped from any alert (#76).
- **Telegram-gated execution.** Every manual trade requires explicit approval. The MCP trade tool cannot fire autonomously; the API trade routes are token-protected and fail-closed.
- **Phased builds (Path C).** Large features ship as Build 1 (foundation/data clock) then Build 2+ (the intelligence on top), proving each layer live before extending. Examples: #50 (intraday capture → ATR detector), #72 (research primitive → persistence/diff), #95 (pump-arm → floor guard → rebuy → re-arm loop), #105 (decision tables → recommendation engine). Keeps each deploy small and verifiable and surfaces real cost/quality data before committing to the expensive half.
- **Decision-memory over re-derivation.** Standing principles are stored (`pm_decisions` / `dev_decisions`) and surfaced at session start so contradictions are caught *before* a build or a trade, rather than re-reasoned each session. Principle changes are superseded (traceable), never silently overwritten. The GHIBLI pump-loop exception to don't-round-trip-memes is the worked example — logged as a deliberate, bounded supersede.
- **`COIN-USD` dash format** for order symbols (Revolut convention); the price map stores both `COIN/USD` and `COIN-USD` keys.
- **Single-write tranche discipline.** Tranche side-effects should happen once, at confirmed fill — not at order placement. Double-writes at placement+fill are the root of the #47 phantom/duplicate class.
- **Crash-safe-clear-first ordering.** Any autonomous-execute path clears its in-memory Map entry (`Map.delete`, sync) *before* the irreversible action (`placeRevolutOrder` etc.). Prevents double-fire on concurrent 30s scan intervals; a crash mid-flight leaves no armed state. Trade-off: a successful action may orphan its journal write on crash — orphaned-action is manually recoverable, double-execute is not. Established in #130, applied in #143 and #125.
- **Live DB is the source of truth.** Narrative — memory, checkpoints, prior summaries — is always to be *verified* against live data, never trusted over it. When they conflict, live wins and the correction is stated explicitly. Re-pull live state immediately before any capital/state-mutating write (a stale read once caused a double-decrement).

- **Detect, don't only prevent (Sept 2026).** A control that constrains a decision cannot tell you the decision failed to execute. The execution watchdog checks outcomes, whatever the cause — two fixes for one silent failure (#391/#392) were what taught this.
- **A notification flag must never gate money movement.** Acknowledgement, "ignore", reminders and de-dupe records are UI state; reading them on an order path is a defect by definition (#391–#393). Likewise `active` means the rule row exists and `loop_enabled` means the loop may act (#396).
- **Fail closed; one authority.** An unreadable pause flag reads as paused; an unverifiable sale is not placed. There is one pause (`ai_auto_execute.enabled`), read fresh at fire time.
- **Clear before you act.** Anything that could fire twice is removed before the order, and restored exactly if the order does not happen.

## 5. Conventions (development workflow)

- **Doc rule (from #626).** A batch that changes behaviour edits this file in the same batch (a §8 row plus the affected section); display-only batches add a §8 row. ARCHITECTURE.md is outside Railway's watch patterns, so a docs-only batch never restarts the server.
- **Copy page and pre-ship (October 2026).** Bryan applies each batch from the Dev thread's copy page. Money-path batches, every new DASHBOARD_WRITES route, every new write keyed by the family page key, and any edit to the key gate go to Fable pre-ship on the desk first; display and records batches go straight to the copy page. Mobile work happens in a Claude Code session with the repo attached and pushes to `mobile-app` only.
- **Batch delivery (current, September 2026).** Changes ship as *batches*: gzip + base64 JSON of exact search/replace edits (anchored by text, never line numbers) with a `base` → `after` SHA-256 guard. Bryan pastes the batch into the **Apply Batch Patch** GitHub Action from a copy page; it refuses a batch built for a different version ("already applied, or out of order"), and may only change `server.js`, `ARCHITECTURE.md` and `public/*.js|html|css`. Every batch is built on the live file, tested (behavioural tests + regression suites), dry-run through a local copy of the Action, then verified live via Railway (deploy SUCCESS + startup log). One fix per batch; trade-path changes ship alone. GitHub's raw file cache can lag a few minutes — check the Railway deployment before concluding a run failed. The Cowork-era bullets below are historical.
- **Canonical build loop (`build_workflow_canonical`).** The standing 11-step process: startup ritual → state model → pull live code (GitHub raw = code-truth) → diagnose read-only → one single-box Cowork prompt → Cowork executes + writes read-back to Drive → Claude verifies the read-back against actual file content → Bryan pushes (`PUSH_NOW.bat`) → Claude verifies boot via Railway MCP → live functional test → log + checkpoint.
- **Read-back-to-Drive workflow.** Cowork writes its read-back to a text file in the `revolut-claude-readbacks` Drive folder; the Dev thread reads it directly (no copy-paste). Bryan only says "done". Read-backs are verified against actual file content — narrative claims ("all edits landed") are never trusted.
- **Single-box Cowork prompts (#64).** Every Cowork prompt is one fenced code block (no nested fences) for one-tap copy. Edits use **search strings, not line numbers** (lines shift every push): find exact block → replace exact block. The prompt's closing checklist enumerates exactly what the read-back must contain (each edit site, `node --check` result, any greps).
- **Boot-verify via Railway MCP.** After every push: `list-deployments` → confirm new commit SUCCESS → `get-logs` types=['deploy'] → confirm Starting Container + Server running + Cron scheduled + auto-exec DISABLED + no errors + any feature-specific log line. No screenshots needed. IDs live in the `railway_ids` preference.
- **Connector-refresh rule.** A new MCP *tool*, or new *typed params* on an existing tool (e.g. a boolean/number), require Settings → Connectors → Revolut X → 'Refresh tool list' before Claude can call the new surface — deploying + clean boot is not enough (the connector caches the schema). A new *action* reusing existing params needs no refresh. (`dev_tools_protocol_addendum`.)
- **Surgical-edit policy (#66).** Targeted edits to `dashboard.js` are acceptable and often preferred over whole-file retransmission; `.bak` backup first; `node --check public/dashboard.js` must pass before every push. Dev decides atomic-vs-surgical per situation.
- **Strategy reconciliation before activation.** Before activating any new rule/strategy on a coin, reconcile against everything already in place for that coin and remove conflicts; state before→after. (A new pump-armed trailing stop once coexisted with a stale manual trailing stop and fired noise alerts — caught by chance.)
- **`node --check` before every push.** Non-negotiable. No deploy without a clean syntax check in the read-back.
- **One change at a time; never bundle across a trade-execution boundary.** Trade-path and capital-sensitive changes ship alone and are verified read-back line by line.
- **Model-usage policy (#67).** Sonnet for light work (reads, verification, small prompts, log writes); Opus for heavy work (feature design, multi-file reasoning, root-cause diagnosis); Fable reserved for the rare heaviest cases. Claude states the recommended model at session start and flags switches; the owner toggles (Claude cannot switch its own model).
- **Session continuity.** Both PM and Dev projects carry custom instructions enforcing a startup ritual (`get_context` → `get_auto_rules` → `get_trading_data include=['dev_log']`) and read a session checkpoint preference (`session_checkpoint_dev` / `_pm`) as "where we left off" — verified against live data. A checkpoint is written at session close. Build specs can be designed in one session (stored as a preference) and executed cleanly in another.
- **Chromebook base64 delivery.** Edit scripts are delivered as base64-encoded Python, chunked into 2-6 `python3 -c` one-liners using `wb`/`ab` file modes. SHA256-verified before running. Avoid double-dash in JS string content inside edit scripts — Chromebook terminal paste auto-converts them to an en-dash (0x96), corrupting the decode. Use single dash or reword.
- **Credential-bug diagnostics.** For auth failures, log only value *lengths* and last-character codes — never the secret. Mobile paste commonly introduces leading/trailing whitespace (root cause of the #12 OAuth `invalid_client` saga: a leading space on the client ID).
